# 长上下文政策：**能装就装**，但不许静默失忆

这份文档解释一个产品判断和它的工程代价。判断来自作者原话：

> 上下文限额加长很多甚至不限额不是问题，大多数用户想要的是达到最佳写作效果，
> 如果写的差再耗费 token 重写也是浪费 token。但是长上下文可能导致的"失忆"问题
> 也确实要解决。

所以这里的取舍不是"要不要省钱"，而是"**省 token 与写对一次，哪个更贵**"。
结论：写作质量优先，预算能装就装；但"预算变大"本身**不是**失忆的解药，
必须同时做三件别的事（位置政策 / 记忆层 / 可检索）。

---

## 一、结论先行

| 决定 | 值 | 依据 |
|------|-----|------|
| 默认上下文预算 | **48000 字符**（原 12000） | 约 3.4 万 token，够装"整章 + 记忆层 + 摘要"；远小于最小预设窗口 |
| 配置上限 | **96000 字符** | 与 `llm_budget.PREFILL_MAX_BONUS` 成对：超时预算必须覆盖它的预填充 |
| 配置下限 | 3000 字符 | 低于此连人设与硬规则都装不下，拼出来只会误导模型 |
| 焦点章正文预算 | 续写/分支/场景 **≤50% 预算**（≥12000）；其他 ≥6000；大纲 ≥1800 | 旧值写死 5000：一章两万字时续写只看得到最后一小截 |
| 长程记忆单块 | 8000 字符（原 3200） | 抗失忆的主手段，两百章的书里旧值只够放十来条 |
| 全局记忆单块 | 6000 字符（原 2400） | 同上（卷级总述 + 未回收伏笔） |
| 超预算怎么办 | **整块让位 + 写进提示词** | 旧实现是"从中间切一刀"，块边界被切碎且没人知道少了什么 |
| 预填充加时 | 每轮 **最多 +60s** | read timeout 覆盖"预填充 + 生成"，预算放大而超时不放 = 重演假"后端没启动" |

数字都在代码里，且都有测试钉着：
`backend/app/core/agent_context.py`（预算与各块上限）、
`backend/app/core/llm_budget.py`（预填充加时）、
`backend/tests/test_context_budget_policy.py`（政策本身 + 跨模块不变量）。

## 二、"限额"到底卡住了什么

`AGENT_CONTEXT_MAX_CHARS` 是**上限**而不是固定开销：拼装量小于上限时它不产生任何
额外 token。2026-09 抽查线上 8 个真实项目，拼装量只有 698–2679 字符（章节最多 5 章），
**没有一个触顶**。所以这次把它从 12000 提到 48000，对**短篇几乎没有任何影响**——
真正变化的是下面三处，它们才是"写长篇时突然变笨"的来源：

1. **焦点章正文**（旧值写死 5000 字符）。续写任务的输入主体就是本章正文；
   一章两万字时，模型看到的只是最后一小截，而"接着写"恰恰最需要整章。
   现在按预算分档，默认给到 24000 字符，真的装不下时标记里会写明省了多少字。
2. **记忆层**（旧上限 3200 / 2400）。跨章连贯靠的是"四十章之前发生过什么"，
   这件事只有长程记忆与全局记忆两层记录。旧上限在长篇里只够放十来条。
3. **超预算时的处理方式**。旧实现把上下文从中段切成两半——块边界被切碎，
   模型与作者都不知道少了什么。

## 三、"失忆"的三条结构性对策

预算变大**不能**解决失忆：Lost in the Middle（arXiv:2307.03172）显示上下文越长，
中段信息的利用率越低。所以除了"能装就装"，还做了三件事：

### 1. 位置政策（`_SECTION_ORDER`）

按"信息在长上下文里的可用性"排序，而不是按拼装顺序：

- **头部**（原样保留）：身份与硬规则、角色卡、关系、地点、bible、时间线、设定条目、
  长程/全局/对话记忆；
- **中段**（量大、超预算时最先整块让位）：章节目录、其他章摘录、工艺卡、参考资料、
  变量、立绘；
- **尾部**（贴着本次请求）：文风、**当前章正文**、用户选区，然后是**再一次**的硬规则
  与输出契约。

### 2. 记忆层（`core/global_memory.py` / 滚动归档）

长程记忆（最近发生了什么）+ 全局记忆（整本书骨架 + 未回收伏笔）+ 章节摘要索引。
这三块是"跨章事实"的唯一载体，所以它们的单块上限随预算一起放宽。

### 3. 可检索：缺什么就取什么

- 上下文末尾写明"提示词里没有的章节或设定就是这次没带来"，并**点名工具**
  （`get_chapter` / `search_script` / `search_lore`）。模型不知道提示词被裁过时，
  会把缺失当成"作者没写"，于是编造或前后矛盾。
- `get_chapter` 默认上限 4000 → **12000** 字符（"取回来只有半章"等于没取回来）。
- 同时修了一处**真 bug**：`get_chapter` / `search_script` / `lint_draft` /
  `polish_prose` 过去只读脚本块（`blocks`），对纯正文工程等于瞎——工具会返回空，
  或者拒绝"这一章只有结构标记（还没写正文）"，而正文明明就在 `prose` 里。
  现在统一走 `agent_context.chapter_plain()`（正文优先，正文为空才渲染块）。

## 四、超预算时的三级处理（每一步都留痕）

```
1) 中段量大的块整块让位（referenceDocs → craft → otherChapters → sprites → variables → index → loreLinks）
2) 仍然超预算 → 再动"可用工具取回"的块与记忆层（lore → chatMemory → globalMemory → longMemory）
3) 最后手段才是首尾保留的字符级压缩（标记里写明省了多少字）
```

- **永不因预算被丢**：身份、硬规则、角色、关系、地点、bible、时间线、文风、
  当前章、用户选区、末尾契约（由 `test_drop_order_never_touches_protected_sections` 结构性断言）。
- 每一次让位都会：① 写进 API 返回的 `included`（界面显示"这次用了什么/省了什么"）；
  ② 写进提示词末尾的「篇幅说明」，并说明用哪个工具能取回。
- 正文截断的标记从"（前文省略）"变成"（本章前 N 字未展开，可用 get_chapter 工具取回整章）"。

## 五、代价：上下文变大 ⇒ 超时必须同步变大

非流式请求的 read timeout 覆盖的是**预填充 + 整段生成**，而预填充耗时随提示词长度
线性增长。上下文预算放大而超时不放，就会重演用户报障过的
「请确认后端已启动」——后端明明活着，只是还没吐出第一个字。

所以 `llm_budget` 增加了一条加时项（`PREFILL_*`）：

```
加时 = min(PREFILL_MAX_BONUS, max(0, 提示词字符数 - PREFILL_FREE_CHARS) / PREFILL_CHARS_PER_SECOND)
     = min(60s, (chars - 8000) / 1500)
```

8000 字符以下不加时（小提示词的预填充是秒级，加时只会让报错变迟钝），
思考档 ×2 与预填充**叠加**。跨模块不变量：

```
(MAX_CONTEXT_MAX_CHARS - PREFILL_FREE_CHARS) / PREFILL_CHARS_PER_SECOND ≤ PREFILL_MAX_BONUS
```

即"允许拼出来的最长上下文，一定落在超时预算能覆盖的范围内"。这条由后端测试
（`test_context_ceiling_is_covered_by_the_prefill_allowance`）与前端契约测试
（`frontend/src/api/timeouts.test.ts` 读同一个 `PREFILL_MAX_BONUS`）双向盯住：
谁单方面放宽上下文上限，谁就得同时放宽预填充加时，并同步前端阶梯表。

前端阶梯相应上调（`TIMEOUTS`）：`quick` 240s→300s、`chat` 300s→360s、
`write` 480s→540s、`long` 600s→660s、`batch` 900s→1020s，
作业轮询 15min→20min。设置页的连通性测试（`/settings/test-llm`，提示词是固定的
`"ping"`）显式豁免预填充加时。

## 六、怎么自查

```bash
cd backend && set PYTHONPATH=. && pytest tests/test_context_budget_policy.py -q
# 政策本身、跨模块不变量、工具取回（正文优先）、丢弃表结构性断言

cd backend && set PYTHONPATH=. && pytest tests/test_context_ordering.py -q
# 位置政策：硬规则首尾各一次、当前章落在尾部窗口、参考文档不挤掉高价值块

cd frontend && pnpm vitest run src/api/timeouts.test.ts
# 逐端点：前端预算 ≥ 后端（基础预算 × 思考档系数 + 预填充上限）+ 余量
```

手边核对预算时：`python -c "from app.core.agent_context import _default_context_max_chars, context_budget_for_model as f; print(_default_context_max_chars(), f('qwen3:8b'))"`
（本地 Ollama 预设是 32k 窗口，会被窗口保护夹小——这是**有意**的：
塞爆窗口会让上游直接拒答，比截断更难善后）。

## 七、仍然没做的事（如实记下）

1. **没有做"整本书塞进上下文"**：1M token 窗口的模型确实装得下，但把全书灌进去
   既不便宜也没必要——摘要 + 记忆层 + 检索的性价比更高，而且长上下文的中段利用率
   更低（见第三节）。这次放宽的是"**该带的别被截**"，不是"什么都带"。
2. **`MAX_CONTEXT_MAX_CHARS` 之上不再放开**：上限由超时预算决定；想再放宽就得承认
   "愿意为一次请求等更久"，同时改 `PREFILL_MAX_BONUS` 与前端阶梯表。
3. **没有做逐块的 token 精确计量**：预算按字符算。字符→token 的估算在
   `_CHARS_PER_TOKEN`（保守取 1.2），只要量级正确，对"要不要加时"没有影响。
4. **窗口保护依赖预设表**（`model_presets.context_window_k`）。用户手填一个没收录的
   模型名时**不缩小**（保持原行为）——收录窗口是我们要还的技术债。
