# 长上下文政策：**能装就装**，但不许静默失忆

这份文档解释一个产品判断和它的工程代价。判断来自作者原话：

> 上下文限额加长很多甚至不限额不是问题，大多数用户想要的是达到最佳写作效果，
> 如果写的差再耗费 token 重写也是浪费 token。但是长上下文可能导致的"失忆"问题
> 也确实要解决。

所以这里的取舍不是"要不要省钱"，而是"**省 token 与写对一次，哪个更贵**"。
结论：写作质量优先，预算能装就装；但"预算变大"本身**不是**失忆的解药，
必须同时做三件别的事（位置政策 / 记忆层 / 可检索）。

---

## 一、结论先行

| 决定 | 值 | 依据 |
|------|-----|------|
| 默认上下文预算 | **48000 字符**（原 12000） | 约 3.4 万 token，够装"整章 + 记忆层 + 摘要"；远小于最小预设窗口 |
| 配置上限（**同步**端点） | **96000 字符** | 与 `llm_budget.PREFILL_MAX_BONUS`（60s）成对：超时预算必须覆盖它的预填充 |
| 配置上限（**流式**端点） | **240000 字符** | 与 `PREFILL_MAX_BONUS_STREAMED`（240s）成对；SSE 有心跳、前端不设总超时（见第七节） |
| 配置下限 | 3000 字符 | 低于此连人设与硬规则都装不下，拼出来只会误导模型 |
| 焦点章正文预算 | 续写/分支/场景 **≤50% 预算**（≥12000）；其他 ≥6000；大纲 ≥1800 | 旧值写死 5000：一章两万字时续写只看得到最后一小截 |
| 长程记忆单块 | 8000 字符（原 3200） | 抗失忆的主手段，两百章的书里旧值只够放十来条 |
| 全局记忆单块 | 6000 字符（原 2400） | 同上（卷级总述 + 未回收伏笔） |
| 超预算怎么办 | **整块让位 + 写进提示词** | 旧实现是"从中间切一刀"，块边界被切碎且没人知道少了什么 |
| 预填充加时 | 每轮 **最多 +60s** | read timeout 覆盖"预填充 + 生成"，预算放大而超时不放 = 重演假"后端没启动" |

数字都在代码里，且都有测试钉着：
`backend/app/core/agent_context.py`（预算与各块上限）、
`backend/app/core/llm_budget.py`（预填充加时）、
`backend/tests/test_context_budget_policy.py`（政策本身 + 跨模块不变量）。

## 二、"限额"到底卡住了什么

`AGENT_CONTEXT_MAX_CHARS` 是**上限**而不是固定开销：拼装量小于上限时它不产生任何
额外 token。2026-09 抽查线上 8 个真实项目，拼装量只有 698–2679 字符（章节最多 5 章），
**没有一个触顶**。所以这次把它从 12000 提到 48000，对**短篇几乎没有任何影响**——
真正变化的是下面三处，它们才是"写长篇时突然变笨"的来源：

1. **焦点章正文**（旧值写死 5000 字符）。续写任务的输入主体就是本章正文；
   一章两万字时，模型看到的只是最后一小截，而"接着写"恰恰最需要整章。
   现在按预算分档，默认给到 24000 字符，真的装不下时标记里会写明省了多少字。
2. **记忆层**（旧上限 3200 / 2400）。跨章连贯靠的是"四十章之前发生过什么"，
   这件事只有长程记忆与全局记忆两层记录。旧上限在长篇里只够放十来条。
3. **超预算时的处理方式**。旧实现把上下文从中段切成两半——块边界被切碎，
   模型与作者都不知道少了什么。

## 三、"失忆"的三条结构性对策

预算变大**不能**解决失忆：Lost in the Middle（arXiv:2307.03172）显示上下文越长，
中段信息的利用率越低。所以除了"能装就装"，还做了三件事：

### 1. 位置政策（`_SECTION_ORDER`）

按"信息在长上下文里的可用性"排序，而不是按拼装顺序：

- **头部**（原样保留）：身份与硬规则、角色卡、关系、地点、bible、时间线、设定条目、
  长程/全局/对话记忆；
- **中段**（量大、超预算时最先整块让位）：章节目录、其他章摘录、工艺卡、参考资料、
  变量、立绘；
- **尾部**（贴着本次请求）：文风、**当前章正文**、用户选区，然后是**再一次**的硬规则
  与输出契约。

### 2. 记忆层（`core/global_memory.py` / 滚动归档）

长程记忆（最近发生了什么）+ 全局记忆（整本书骨架 + 未回收伏笔）+ 章节摘要索引。
这三块是"跨章事实"的唯一载体，所以它们的单块上限随预算一起放宽。

### 3. 可检索：缺什么就取什么

- 上下文末尾写明"提示词里没有的章节或设定就是这次没带来"，并**点名工具**
  （`get_chapter` / `search_script` / `search_lore`）。模型不知道提示词被裁过时，
  会把缺失当成"作者没写"，于是编造或前后矛盾。
- `get_chapter` 默认上限 4000 → **12000** 字符（"取回来只有半章"等于没取回来）。
- 同时修了一处**真 bug**：`get_chapter` / `search_script` / `lint_draft` /
  `polish_prose` 过去只读脚本块（`blocks`），对纯正文工程等于瞎——工具会返回空，
  或者拒绝"这一章只有结构标记（还没写正文）"，而正文明明就在 `prose` 里。
  现在统一走 `agent_context.chapter_plain()`（正文优先，正文为空才渲染块）。

## 四、超预算时的三级处理（每一步都留痕）

```
1) 中段量大的块整块让位（referenceDocs → craft → otherChapters → sprites → variables → index → loreLinks）
2) 仍然超预算 → 再动"可用工具取回"的块与记忆层（lore → chatMemory → globalMemory → longMemory）
3) 最后手段才是首尾保留的字符级压缩（标记里写明省了多少字）
```

- **永不因预算被丢**：身份、硬规则、角色、关系、地点、bible、时间线、文风、
  当前章、用户选区、末尾契约（由 `test_drop_order_never_touches_protected_sections` 结构性断言）。
- 每一次让位都会：① 写进 API 返回的 `included`（界面显示"这次用了什么/省了什么"）；
  ② 写进提示词末尾的「篇幅说明」，并说明用哪个工具能取回。
- 正文截断的标记从"（前文省略）"变成"（本章前 N 字未展开，可用 get_chapter 工具取回整章）"。

## 五、代价：上下文变大 ⇒ 超时必须同步变大

非流式请求的 read timeout 覆盖的是**预填充 + 整段生成**，而预填充耗时随提示词长度
线性增长。上下文预算放大而超时不放，就会重演用户报障过的
「请确认后端已启动」——后端明明活着，只是还没吐出第一个字。

所以 `llm_budget` 增加了一条加时项（`PREFILL_*`）：

```
加时 = min(PREFILL_MAX_BONUS, max(0, 提示词字符数 - PREFILL_FREE_CHARS) / PREFILL_CHARS_PER_SECOND)
     = min(60s, (chars - 8000) / 1500)
```

8000 字符以下不加时（小提示词的预填充是秒级，加时只会让报错变迟钝），
思考档 ×2 与预填充**叠加**。跨模块不变量：

```
(MAX_CONTEXT_MAX_CHARS - PREFILL_FREE_CHARS) / PREFILL_CHARS_PER_SECOND ≤ PREFILL_MAX_BONUS
```

即"允许拼出来的最长上下文，一定落在超时预算能覆盖的范围内"。这条由后端测试
（`test_context_ceiling_is_covered_by_the_prefill_allowance`）与前端契约测试
（`frontend/src/api/timeouts.test.ts` 读同一个 `PREFILL_MAX_BONUS`）双向盯住：
谁单方面放宽上下文上限，谁就得同时放宽预填充加时，并同步前端阶梯表。

前端阶梯相应上调（`TIMEOUTS`）：`quick` 240s→300s、`chat` 300s→360s、
`write` 480s→540s、`long` 600s→660s、`batch` 900s→1020s，
作业轮询 15min→20min。设置页的连通性测试（`/settings/test-llm`，提示词是固定的
`"ping"`）显式豁免预填充加时。

## 七、"要不要为了无限上下文换架构"（结论：不必大改，按执行档分两档就够）

上一轮说过"想真正无限得先换架构"。把这件事查清楚之后的结论是：**不需要换架构，
但也确实不能只调一个数字**——要区分"谁在等"。

### 7.1 真正的约束是什么

天花板不是模型窗口给的（默认模型是 1M token 窗口），而是**我们自己的超时预算**：

```
非流式请求的 read timeout 必须覆盖：预填充（随提示词线性增长） + 整段生成
```

所以"能放多大的上下文"等价于"**谁在等这次请求、能等多久**"：

| 端点类型 | 谁在等 | 能等多久 | 于是 |
|---|---|---|---|
| 同步端点（`/agent`、审稿、回信、门禁…） | 前端按"这个 HTTP 请求"计时，有阶梯预算 | 被前端阶梯卡死 | 上下文天花板 96k 字符、预填充加时 +60s |
| 流式端点（`/agent/stream`、`/pipeline/run?stream`） | 浏览器看进度，SSE 20s 心跳保活，**前端不设总超时** | 只受"多久没有新字节"约束 | 天花板 240k 字符、预填充加时 +240s |

也就是说：**架构（SSE + 心跳 + 作业化）已经在关键路径上了**，
缺的只是"流式路径没有用满它换来的宽松度"。所以这一轮做的是按执行档分两档，
而不是重写链路。

### 7.2 落点（`core/execution_profile.py`）

请求级 ContextVar `PROFILE_SYNC` / `PROFILE_STREAMED`（与 `core/usage.py` 的 kind 同一套做法）：

- **默认必须是同步档**：认不出的值、没设置的路径一律按保守档走——否则同步端点会拿到宽预算，
  前端先掐断，用户又看到"后端是不是挂了"（这一类问题已经踩过）。
- 只有流式路由显式 `set_profile(PROFILE_STREAMED)`（`/agent/stream`、
  `/pipeline/run?stream`）；**有源码级守卫测试钉住"这行只能出现在流式处理函数里"**。
- 两档各自满足同一条跨模块不变量：
  `(天花板 - PREFILL_FREE_CHARS) / PREFILL_CHARS_PER_SECOND ≤ 该档预填充加时上限`。
- 窗口保护仍优先：32k 窗口的本地模型在**任何档位**都被夹到 ~19k 字符。

代价如实记着：240k 字符 ≈ 17 万输入 token **每次调用**（多步 Agent 要乘步数）。
所以它是上限不是目标，真正的判据在下一节。

### 7.3 判据：先量，再决定要不要动它

`GET /admin/llm-latency` 现在给两类数据（进程内、有界窗口，边界见 `core/latency_stats.py`）：

1. `promptChars` 的分位（每次出站提示词多大）——**上下文预算有没有被用满**；
2. `context|<task>` 系列的 `truncationRate`（拼装时是否发生过截断/整块让位）。

读法：

| 观测 | 结论 |
|---|---|
| `promptChars` p95 远低于天花板、`truncationRate` ≈ 0 | 预算没卡住写作，调大（或换架构）是白花钱——这也是 2026-09 抽查线上 8 个项目（拼装量 698–2679 字符）的预期结果 |
| `promptChars` p95 贴着天花板、`truncationRate` 明显 > 0 | 真的被卡住了：先确认是不是"该检索的没检索到"，再考虑继续抬流式档天花板 |
| `firstToken` p95 已经接近该档预填充上限 | 该换的不是天花板而是**上游**（更快/更近的端点，或把长前缀固定下来吃上下文缓存） |

换句话说：**换架构不是第一步，量出来才是**。真要走到"每次请求塞进整本书"，
该做的是 job 化长上下文生成 + 上下文缓存，而不是继续抬数字。

## 八、仍然没做的事（如实记下）

1. **没有做"整本书塞进上下文"**：1M token 窗口的模型确实装得下，但把全书灌进去
   既不便宜也没必要——摘要 + 记忆层 + 检索的性价比更高，而且长上下文的中段利用率
   更低（见第三节）。这次放宽的是"**该带的别被截**"，不是"什么都带"。
2. **同步档的 96k 之上不再放开**：它的上限由前端阶梯决定；想再放宽就得同时改
   `PREFILL_MAX_BONUS` 与前端阶梯表（有跨模块不变量测试盯着）。流式档是 240k，
   同样成对（`PREFILL_MAX_BONUS_STREAMED=240s`）。
3. **没有做逐块的 token 精确计量**：预算按字符算。字符→token 的估算在
   `_CHARS_PER_TOKEN`（保守取 1.2），只要量级正确，对"要不要加时"没有影响。
4. **窗口保护**：预设表收不全（自建端点、自部署模型、厂商新名字），所以做了三层：
   - 预设表能认出来的模型：按它的 `context_k`；
   - 认不出来的：按服务端保守假设 `UNKNOWN_MODEL_WINDOW_K`（128k token ≈ 76.8k 字符），
     可用 `AGENT_UNKNOWN_MODEL_WINDOW_K` 覆盖（0 或负数 = 不夹）；
   - **用户自己声明**（账号设置「上下文窗口（千 token）」）：
     已知模型取 `min(预设, 声明)`——声明只能调低，不可能超过厂商窗口；
     未知模型直接以声明为准（他自己知道自建端点的窗口，比我们的假设准）；
     `-1` 表示明确不夹。
   声明值是**账号级**的（窗口与设备无关），请求级通过 `execution_profile` 的
   ContextVar 传递——所有"解析凭据"的路径都会带上它（`resolve_llm_credentials` 一处设置）。
   本机存储（X-LLM-* 头部）模式不声明窗口，那类用户走服务端保守假设。
   遗留：**没有**"按项目"声明窗口（一本书换模型窗口是很少见的场景，先不做）。

## 九、作者能看到什么（"失忆"的可观测面）

上下文被裁过却没人告诉作者，是"AI 怎么忘了"最常见的来源。所以这一轮把三个量摆到界面上：

- `contextMeta.charsUsed` / **`budgetChars`** / **`truncated`**（`domain/types.AgentContextMeta`
  新增后两个）随 Agent 响应返回；
- Agent 面板每次回答后显示一行"本次上下文 12,480 字（上限 48,000）"，被裁过时用告警色并附一句
  可执行的话：「有资料没装下，需要那段前情时直接让它用 `get_chapter` 取第 N 章」；
- 同一行的数据也进统计（`context|<task>` 系列），能在管理员面板看到**截断率**，
  而不只是单个用户的体感。

**"没装下的是什么"要具体到能照着做**（`AgentContextResult.budgetReport` → `contextMeta.budgetReport`）：

| 字段 | 内容 | 界面怎么用 |
|---|---|---|
| `includedSections` | 这次**真的带上**的资料块（key + 人话名） | 状态行那句"参考 角色卡·设定条目·当前章"——**不再用正则去猜 `included` 里的中文串**（旧写法每加一个资料块都得同步改正则，漏了就不显示） |
| `droppedSections` | **因为篇幅**整块让位的资料 + `retrieve`（怎么取回来） | 「没装下的 N 项」清单，每行一句可执行的话 |
| `trimmedParts` | 被截断/压缩的内容（当前章正文"只带了末尾 24,000 / 60,000 字"、其他章摘录压成摘要、中段压缩） | 同上，正文那一条会写明"让它用 get_chapter 读第 X 章的完整正文" |
| `excludedByTask` | **按任务省去**的（立绘、变量这类机制资料） | 单独一句折叠说明：这类资料对写正文没有信息量，**不是"没装下"** |

最后一条的区分很重要：把"设计如此"和"真的没装下"混成一句，作者会去关一堆本来就不该带的资料。

展示口径在 `lib/contextUsage.ts`（6 项测试）与 `lib/contextBudget.ts`（9 项测试）里钉住：
**缺的字段不编**——旧后端没有 `budgetChars` 时只显示已用量，不显示"上限 0"；
没有被裁过时那一块整块不出现（不是显示"0 项"）；取回动作原样用后端给的字符串，
前端**不在本地编工具名**（写错工具名比不写更糟）。
管理员面板新增「LLM 耗时 / 上下文」卡片（`lib/latencyReport.ts`，11 项测试），
其中一条专门防单位混淆：上下文系列的 `total` 是**字符**，不能按秒渲染成 "p95 47000.0s"。
