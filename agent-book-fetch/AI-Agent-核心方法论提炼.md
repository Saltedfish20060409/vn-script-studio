## 引言（Introduction）

1. 用可解释、可验证、可复用的工程原则设计 Agent，每项设计决策对应明确的能力边界与工程取舍，而不是靠经验和直觉反复试错。
2. 核心公式 Agent = LLM + 上下文 + 工具（直觉层：大脑+眼睛+手脚），对应 RL 形式化：Policy / Observation Space / Action Space，三者缺一不可。
3. 实践在前、命名在后：术语往往是大量实践经验的归纳而非实践起点；当一个概念成为共识时，问题往往已被领先系统探索多年。
4. 选择对 Agent 能力上限提出足够高要求的真实业务（长流程、高风险、涉及真实经济利益），让持续的真实反馈暴露模型能力与业务要求之间的差距。
5. 建立系统的评估（Evaluation）机制：没有评估就无法区分真实提升与随机波动，把迭代从经验判断转化为可比较、可复现的工程过程。
6. 架构原则应穿越模型迭代周期：好的设计描述的是智能系统与世界交互的基本模式，而非某个特定模型的用法。
7. 用提议者-审核者（proposer-reviewer）双视角方法解决模型过早认为任务完成的问题（先于 loop engineering 概念的成熟实践）。
8. 采用口述式协作（whisper coding）等人机协作方式，缩短"提出问题→检索资料→形成草稿→复核修改"的迭代周期来生产知识产品。

## 第二章 上下文工程

1. 上下文质量决定 Agent 能力上限：一个中等模型配精心组织的上下文常胜过顶级模型在信息匮乏下的盲目摸索；上下文 = 静态前缀（系统提示+工具定义）+ 动态轨迹（消息历史）。
2. 系统提示词和工具定义一旦确定就不要改：任何字节变化（哪怕多一个空格）都会使 KV Cache 从首个不同 token 起失效，改动越靠前，延迟与成本影响越大。
3. 动态信息（时间戳、用户状态、运行状态）永远追加到消息末尾而不是修改前缀；使用标准 API 格式、不自行拼接消息（偏离 Chat Template 会削弱模型多步思考与工具调用能力）。
4. 提示词设计用"新员工测试"检验：一个聪明的新员工读完还不知道怎么做，Agent 也一样；流程驱动（标准操作流程 SOP）优于上百条零散规则堆砌。
5. 业务规则必须细化到可执行程度（作用域+动作+例外+验证方式），不给模型过多业务裁量权——产品经理定规则、工程师负责编码进提示词。
6. 难以用规则精确描述的输出，用两三个高质量 few-shot 示例胜过等量篇幅的抽象规则；示例集固定且字节级稳定（按请求动态检索示例会持续破坏缓存）。
7. 工具描述要写清"何时用"与"做不到什么"（反例边界），参数用具体例子而非抽象规范；当 Agent 频繁选错工具时优先检查工具描述而不是换模型。
8. Agent Skills 采用渐进式披露：只常驻 name+description 目录（数百 token），需要时再加载完整正文，避免提示词膨胀与注意力稀释；description 应写成路由条件（"何时该用我"），并给反例减少误触发。
9. 用 Agent 状态栏把隐式状态（TODO 列表、工具调用计数、时间戳、详细错误信息）显式化为结构化元信息注入轨迹末尾，小模型准确率可接近大模型、思考 token/延迟/花费可降约一个数量级。
10. 状态栏尽量用代码确定性维护而非 LLM 统计（模型几乎无条件信任状态栏内容）；状态栏是对原始上下文的有损投影，删除原文前须确认没有未预算的查询维度。
11. 上下文压缩有三大动机：长度与成本约束、提升思考质量（把"需要思考得出的结论"变成"可直接检索的知识"）、缓解上下文焦虑；压缩对象是历史中的 tool results，应在接近阈值时批量压缩而非每轮压缩（频繁压缩破坏缓存）。
12. 压缩设计四条原则：信息价值非均匀分布（决策点>支撑证据>噪声）、语义完整性（关键事实不可丢）、任务相关性（检索保广度、分析保深度、创作保留灵感触发点）、压缩即理解（负责压缩的模块要接近主模型能力）。
13. 上下文感知压缩：把查询意图与已积累信息纳入压缩提示（"Given the search query + Current context"），token 使用量可减少 75% 以上；关键事实可附引用以保留无损溯源。
14. 隔离优于压缩：把"在代码库大范围搜索"这类产生海量中间内容的探索委派给独立子 Agent，只把结论性摘要回传主上下文（任务描述须自包含）。
15. 提示注入的上下文层防御：来源标记（external_content 标签）、结构化角色区分"指令与数据"、输入清洗；上下文层只是第一道防线，须配合执行层权限控制与沙盒。

## 第三章 用户记忆和知识库

1. 记忆提取须同时满足三规则：选择性（丢弃短期细节）、抽象化（把具体事件归纳为长期偏好）、结构化（用可检索的字段保存事实）。
2. 用三层次框架评估记忆系统：基础回忆→多会话检索→主动服务，逐层递进；"主动服务"（跨会话发现隐藏关联并主动预警）要求系统同时握有"全局概览"与"精确细节"。
3. 记忆分层存放：轨迹（append-only 原始记录）、用户长期记忆（跨会话档案，可改写/合并/淘汰）、业务状态；记忆层次（放哪里）×存储格式（怎么存）×认知类型（存什么）三套体系正交可自由组合。
4. 四种存储格式按需选择：Simple Notes（O(1) 低成本）→Enhanced Notes（语义完整）→JSON Cards（支持部分更新）→Advanced JSON Cards（加 backstory/person/relationship 实现同名实体消歧）；关键少量数据用 Cards、大量非关键事实用 Notes、生产用混合模式。
5. 用认知科学三类记忆指导"存什么"：情景记忆（具体事件）、语义记忆（一般知识）、程序记忆（行为流程），Agent 端均有直接对应（如"用户是素食者"=语义记忆）。
6. 记忆冲突处理倾向"仅追加写入+混合检索"（Mem0 v3 路线）：只做 ADD，让带时间戳的多条事实并存，查询时融合语义+BM25+实体匹配+时间排序确定当前事实，避免写入时误 UPDATE/DELETE 不可逆丢失历史。
7. 记忆压缩三层机制：重要性评分（访问频率/时间衰减/情感强度/信息独特性）筛选→聚类生成代表性摘要→抽象泛化（情景记忆提炼为语义/程序记忆）。
8. 隐私保护：用本地部署的 LLM 做日志脱敏（敏感日志不送云端），识别结构化/半结构化/自然语言敏感内容，超高吞吐场景用"正则快速过滤+LLM 深度分析"混合策略。
9. RAG 分块三策略：固定大小+重叠、递归/结构感知（生产默认）、语义切分；块大小 256-1024 token、重叠 10%-20% 为常见起点，按检索质量实测调优。
10. 混合检索三段式：稠密+稀疏并行检索→RRF 倒数排名融合（只看排名，得分=Σ1/(k+rank)，k≈60）→神经重排序（cross-encoder 对候选池前 50 精排）；融合与重排各自不可替代。
11. 检索质量用 recall@k（命中率口径）、MRR、nDCG 度量，并报告"检索失败率"（正确信息未进 top-k 的查询比例）。
12. 知识库不能只放原始案例：须在索引阶段主动提炼——把 100 个个体案例压缩为统计摘要、把散落工单提炼为带明确边界的规则卡，否则模型会因最近邻偏置、边界语义缺失、完整性信号缺失而误判。
13. 结构化索引按查询类型选择：多数查询用混合检索即可；跨文档综合/多层次导航才值得上 RAPTOR（树状摘要，适合"概念→细节"）或 GraphRAG（实体关系图，适合"谁和谁什么关系"、多跳推理与实体消歧），代价是更多 LLM 调用。
14. 知识更新按"代码库+PR"流程：Proposer Agent 先检索已有知识再提最小 diff，Reviewer Agent 独立对照原始证据审核（拒绝意见要指向具体证据与行号），迭代收敛、CI 重建索引后才合入；原始证据层（只增不改）、知识层（可修订）、服务层（派生索引）三层分离。
15. 异源互审：Proposer 与 Reviewer 使用能力相近但来自不同家族的模型（如 Claude 配 GPT、DeepSeek 配 Kimi），降低同源偏见；权限强制分工——Proposer 只写工作分支、Reviewer 只读证据、只有合并流程可更新主库。
16. 定期全量整理（睡眠学习在知识管理中的应用）：去重/去旧/合并、回到原始数据逐段核查（防止摘要代际传错）、冲突用"场景限定（qualification）"解决而非简单保留最新；产物同样走 PR+异源审核，按时间或质量阈值触发。
17. 上下文感知检索（Contextual Retrieval）：索引前用 LLM 为每个 chunk 生成含背景的前缀摘要再拼接索引（补前缀做加法，与运行期"上下文感知压缩"做减法相反），同时增强稠密与稀疏检索，检索失败率降 49%、加重排降 67%。
18. 双层记忆架构实现"主动服务"：Advanced JSON Cards 把少量关键事实结构化常驻上下文（随时可见的概览）+ 上下文感知检索按需取回原始对话细节；只靠常驻会丢细节、只靠检索缺全局视野。

## 第四章 工具

1. 能力表达形式三维决策框架：参数复杂度（嵌套/联合校验用专用工具 schema）、变更频率（频繁变化的能力用 Skill，改文本远便宜于改代码）、模型能力（弱模型需要结构化工具引导，SOTA 模型可用 Skill+通用执行器）。
2. 工具粒度权衡：功能相似且使用场景重叠→整合为一个工具（read_document + file_type 参数）；参数集差异大或某功能使用频率极高→保持独立（grep/find 单列）。
3. 通用工具优于专用工具，除非存在明确的安全、权限或性能理由：code_interpreter 在沙盒里替代十几个专用计算器，给 Agent"元能力"。
4. 工具描述四要素：写"何时用"而非"能做什么"；明确边界与反例（做不到什么）；参数用具体例子（"RFC3339，例如 2024-03-15T14:30:00Z"）；说明返回结构与执行代价；每个工具附 1-5 个真实调用示例（工具调用准确率可从约 72% 提到 90%）。
5. 参数传递保真性：模型感知的世界与工具操作的世界不能有系统性偏差——禁止静默转换/静默注入参数（如把弯引号悄悄转直引号），规范化必须在工具描述中说明并告知模型。
6. 感知工具设计：返回结构化候选列表+分页/游标（不倾倒全文）；读取工具支持 offset/limit；静默截断是危险的，必须显式标示省略量与续读方式；输出超阈值（如 10K 字符）时按当前查询意图自动压缩；只读性带来安全缓存与并行执行的红利。
7. 多模态感知三条技术路线按需选择：原生多模态（图表/布局理解最佳但费 token）、提取为文本（纯文字文档最省 token，但丢版式）、工具化多模态分析（主模型不支持时，把"文件+问题→分析结果"封装为工具，上下文只留简短问答）。
8. 执行工具安全分层设计：输入验证（快速失败，不"智能修正"）→权限控制（工作目录/黑名单/配额，黑名单不是唯一手段）→提议者-审核者审批→Sidecar 实时门控。
9. 提议者-审核者两种机制：事前审批（不可逆操作；两模型须不同家族、能力相近、底层规则完全一致，但关注点不同——提议者行动导向、审批者风险导向；拒绝理由作为工具结果进入轨迹）；事后验证（要诀是模态切换——渲染为视觉检查排版、在沙盒运行验证配置生效，避免同模态盲区）。
10. Sidecar 机制：独立轻量 LLM 与主模型流式输出并行，只读结构化字段（{tool, command}）判断工具调用是否安全（隔离自由文本以堵住提示注入话术），配拒绝熔断器（连续拒绝转人工）。
11. 执行-验证-反馈闭环：write_file 后立即自动跑 linter、把结构化错误列表返回给 Agent；长输出保留头尾+存盘+文件引导；执行环境按风险选进程级/容器/microVM 隔离（venv 不是沙盒）。
12. 幂等性与"预检-确认"：让操作携带唯一标识去重或"先查询后变更"；邮件、转账等不可撤销操作用两段式——第一段用不同模型家族的模型+专用安全检查提示词校验，第二段执行，失败不盲目重试。
13. 子 Agent 提示词四要素：角色定义清晰、上下文来源明确标注（[FROM_MAIN_AGENT]/[FROM_USER]/[TOOL_RESULT] 防注入）、任务边界明确（什么需转交/上报）、输出格式标准化。
14. 主动工具发现：系统提示只保留少数基础工具+一个"工具搜索工具"，Agent 在执行中声明能力缺口→按"服务器级→工具级"两层语义路由匹配注入；新工具 schema 追加到轨迹末尾（保持前缀缓存），低相似度明确返回"未找到"让 Agent 改写需求或手工实现。
15. MCP 统一互操作但慎防上下文开销：只暴露工具名索引、按需查询完整定义（token 可减 46.9%）；接入第三方服务器须审查工具描述（当作不可信输入）、锁定版本、最小权限凭证，防同名工具遮蔽与凭证风险。

## 第七章 Agent 的评估

1. 评估对象是"模型+Harness 组合体"而非模型本身：用模型替换实验（固定 Harness 换强弱模型）区分瓶颈在模型还是 Harness，用消融实验（逐关组件）定位 Harness 内哪个部件重要。
2. 区分两种指标口径：Pass@k / Best@k 测能力上限（"技术奇观"，给足机会至少成功一次）；Pass^k（连续 k 次全部通过）测业务可靠性；评估报告必须写清 k 的口径（独立采样 vs 生产流水线连续任务）。
3. 补充过程指标：行动合法率、工具调用正确率、路径效率（步数/冗余动作/回退次数）、检索覆盖率、成本与延迟；安全与合规零容忍——一次严重违规即一票否决整体评价。
4. 轨迹与结果双重覆盖：Agent"说了什么、做了什么"（轨迹）与"系统最终变成什么样"（结果）是两件事，两类评测都要做，避免"说了但没做到"与"路径走歪但结果碰巧对"两类盲区。
5. 评判者校准：放量使用 LLM 评判前，先构建 100-200 例人工标注金标集，测评判模型与人类的一致率（kappa≥0.7）后才启用；Rubric 或评判模型每次更新后重新校准。
6. 对抗式评审（红队）：主动构造"表面完美但含隐蔽错误""关键词堆砌蒙混""利用评判模型已知偏见骗分"的挑战案例，压测评估体系。
7. 评估环境五要素：数据集、环境状态（真实性与可控性平衡、每次可重置）、工具接口（提供原子操作而非"解决用户问题"式高层抽象）、评分标准（Rubric）、执行协议。
8. 人机交互型评估的核心是渐进式信息透露：模拟用户不能一开始把完整需求全盘托出，须按需逐步透露信息、设置有限耐心、遵循固定脚本保证可复现（τ²-bench 的双控环境还让用户模拟器真正操作共享环境）。
9. 数据集设计五挑战：明确性与开放性张力、真实性与可控性平衡（SWE-Bench Verified 人工筛选 2294→500 题提信噪比）、多样性与系统性（参数化模板生成无限变体+能力标签诊断短板）、成本与覆盖（GAIA 466 题分三级）、数据泄漏防范（动态参数、canary GUID、验证基于最终状态而非操作序列）。
10. 任务难度层次化：三级难度对应不同改进方向（基础工具使用→多步规划与信息整合→长序列思考与复杂性管理），让评估结果可诊断具体能力短板。
11. 可验证性设计：答案用严格格式保证唯一性（字符串匹配即可判对）；双重验证 FAIL_TO_PASS + PASS_TO_PASS（证明修复且未引入新 bug）；深层状态检查（不只看报告文件，直接查数据库/DOM/后端确认真正生效）。
12. Rubric 四准则：(1) 基于专家指导——必须反映领域知识，捕捉核心事实与推理步骤；(2) 全面覆盖——涵盖准确性、连贯性、完整性、安全性，并明确陷阱（高风险常见错误）；(3) 按重要性加权——必要/重要/可选/一票否决项（Veto）；(4) 评价标准自包含——每个评分档给出可验证的具体行为，而非"展示深刻理解"式抽象标准。
13. 防评判偏见：长度偏差（Rubric 显式惩罚冗长、规定长度上限、定期审计评分与长度相关性）；位置偏差（配对比较交换顺序各评一次取平均，或两次判决一致才计入）；同源模型问题（古德哈特定律——Agent 会钻评判模型偏好与盲点，用不同家族多个评委多源异构评判、相同 Rubric、加权平均/一致性检查聚合）。
14. 防奖励作弊（reward hacking）：明确惩罚幻觉、讨好用户、关键词堆砌、回避棘手问题；Rubric 通过试用收集分歧不断迭代为"判例集"。
15. 失败归因：端到端评估要回答"从哪一步开始失败"——标出主要错误类别、首个不可接受行为的步骤、对应工具调用与可复核证据；后续错误多为连锁反应，按"最早且能解释后续失败"选主因；归因需人工参与（产品问题），不能只靠 LLM。
16. 回归任务两层互补：端到端回归（验证完整工作流不退化）+ 轨迹前缀回归（冻结首个错误前的上下文，只验证下一步决策，答案定义为"可接受动作集合+禁止动作"）；轨迹前缀集对高可靠性生产系统往往更重要、成本更低。
17. 统计显著性：SE≈√(p(1-p)/n)；同一批任务比较两配置用配对分析（McNemar/配对 bootstrap）而非直接相减独立成功率；每配置 3-5 个随机种子报告均值与波动；分差须超过噪声、配对成立且可复现才做切换决策。
18. 评估驱动的改进闭环：看到分数下降先检查评测系统本身再动 Agent（资源不足/评分器 bug/用例脱节都会伪造成退化）；读 Benchmark 报告先找失败簇（按任务/能力标签）再回放轨迹，分清"看/想/做/验"哪个环节；一轮只改一个变量（观察→假设→实验→验证），小样本结论只用于决定下一步是否扩大测试。
19. 内部评估基础设施五件套：消融总开关（每个特性可独立关闭、定期验证真实贡献，防"特性债务"）、AB 测试方法论（多臂渐进变体、区分机制指标与目标指标、设护栏指标、记录基线统计）、双层特性开关（编译时+运行时，服务实验/渐进发布/紧急熔断）、提示词敏感性评估（确定性渲染+版本化快照+每次变更跑回归，提示词也是"代码"）、隐私感知分析（类型系统强制约束）。
20. 从评估到训练：一套清晰的 Rubric/验证器本质上就是 RLVR 的奖励函数；仿真环境需满足确定 reset 语义与远超评估的吞吐（百万级 episode），评估资产可近乎无缝转成训练信号。

## 第九章 Agent 的持续进化

1. 保存经历不等于从经历中学习：学习发生在系统主动完成"评价→对照→归纳→验证"之后；起点不是"总结"而是"评价"——错误的评价一旦进入长期知识、提示或训练数据，影响会跨任务放大。
2. 三层验证结构：结果验证器（读测试/数据库状态/工具返回，回答"是否真的办成"）→过程验证器（检查业务规则/权限/动作序列，回答"是否以允许的方式办成"）→质量验证器（按 Rubric 评价语言与策略，回答"是否办得合适"）；越靠下的指标越应依赖代码与环境真值。
3. 评价维度拆分才有诊断价值：客服轨迹至少覆盖任务结果、规则遵从、隐私边界、事实可靠性、承诺-行动一致性、表达质量、合规变通七维，替代单一的"用户满意度"（用户可能因违规退款而满意）。
4. 四种进化载体按能力表示性质选择：事实/经验规律→知识库；可语言说明的判断原则→Prompt/Skill；可确定执行的高风险硬约束→程序/Harness；高维感知、生成风格、隐式策略→模型参数；同一能力可拆分到多个载体（路由结果只是更新提案，尚无发布资格）。
5. 知识提炼五步管道：保存不可变轨迹→单次运行结构化分析（任务类型/所需能力/策略/错误/例外）→按任务族聚类并建立"哪些轨迹支持、哪些反驳"的证据表→达到支持门槛才写入正式文档→在未参与提炼的新任务上测迁移效果。
6. 成功轨迹贡献策略草案、失败轨迹贡献排除性知识、部分成功轨迹帮助识别"哪一段有效"；Reflexion 式自然语言反思可参与生成草案，但反思本身不是证据——只有与环境结果相符、获跨轨迹支持并在新任务上正向迁移的内容才进入正式经验。
7. 系统提示学习：当多条相似轨迹反复暴露同一种可用语言描述的策略错误时，才把经验升级为指令；更新是"带来源的最小 diff"而非重写整份 Prompt；待验证版本必须在触发失败的边界集上改善、在正常工作的保留集上不退化，才进入灰度。
8. 经验写成程序（PreAct 范式）：把探索轨迹编译为参数化工作流（字面量变模板变量）→定义动作前后检查与最终状态检查→独立回放验证（重置到独立初始状态完整回放）→匹配回放（不逐步调用 LLM，重复任务 8.5-13 倍加速）→失效时回退到完整 Agent 重学；没有三重验证的加速只是"更快地重复错误"。
9. 自我修改按可审计的软件发布流程执行：从稳定版本创建隔离更新分支→Coding Agent 生成最小补丁→依次通过静态检查/单元测试/安全扫描/失败轨迹重放/旧任务回归→灰度部署；每个修改请求是"可证伪的变更契约"（失败证据+推断根因+归属组件+修改提案+预期修复+可能受损行为+各自验证用例）。
10. 提案生成器的输入不只失败案例：还须包含必须保留的成功行为与曾被拒绝的修改记录（Self-Harness），失败证据+成功约束+历史尝试构成有边界的方案空间，比无差别塞入全部源码更易产生局部可验证的改动。
11. 持续进化的三道安全边界：证据与指令隔离（网页/工具输出/LLM 摘要都是不可信证据，不能当指令执行或直接纳入 Skill，须按固定 schema 提取主张+原文位置+来源）；待验证能力与正式能力隔离（新代码/依赖先过沙盒、权限检查、供应链扫描与行为测试）；安全机制不可自我修改（验证器、测试用例、发布门槛、审计日志、稳定备份都在 Agent 修改权限之外）。
12. 睡眠学习五步：触发（时间/轨迹数/容量/错误率门槛且无高优先级在线任务）→定向（读取已有能力与不可修改边界）→采集与整合（从已评价轨迹找新信号、合并重复、标记冲突、优先局部补丁）→验证与审批（迁移集+保留集+安全集，高风险等人工批准）→修剪与索引（过期标记/归档/删除，保留来源与回滚版本）。
13. 持续进化长期评价五类结果：回退（新经验与旧经验冲突）、泛化（未覆盖场景的提升）、Token 效率、安全性（规则/隐私/拒绝边界是否漂移）、长期工程质量（维护复杂度/一致性/兼容性）；只解决当前失败案例却在别处退化不是成功的学习。
14. 区分 harness-updating 与 harness-benefit：更新器产出了有价值的修改 ≠ 任务 Agent 在运行时找到、激活并正确使用这些修改；用分层指标评估（更新提案有效率、产物激活率、遵循成功率、保留任务集增益），不能只用端到端分数反推更新器好坏。
15. 开放任务的证据结构（面向无法自动验证的目标）：结论与证据分离（每类声明链接可审计来源）、保留负面结果（失败实验/被拒提案/停止原因入日志）、维护搜索多样性（保留类型不同的低分分支）、让人类在更高层介入（定义问题、审查评价标准、解释反常结果、决定何时停止）。
16. 在线执行与离线学习分离（双循环结构）：在线循环只完成任务并追加不可变证据，离线进化循环聚合轨迹→诊断根因→生成更新提案→验证门槛→发布新版本；防止偶发成功、网络故障或恶意输入立即改写长期能力。
17. 持续学习至少包含四环节——记住、迁移、更新、保持：最终分数高但仍在用已废止规则、靠违规捷径或更新后破坏原有能力，都不能判定为持续进化（对照实验：静态记忆 vs 只追加记忆 vs 可替换/可淘汰的版本化记忆）。

## 与 AI 审稿/内容评估最相关的跨章节方法论

（面向"用 LLM 评估小说/剧本写作质量"的具体方法，每条注明来源章节）

1. **Rubric 四准则设计审稿评分维度**（第7章）：审稿 Rubric 须基于专家指导（叙事结构、人物弧线、节奏、主题、对话人设等文学专业维度，而非只评流畅度）、全面覆盖正面标准与陷阱（cliché、巧合化解矛盾、信息倾倒、工具人角色、烂尾等常见硬伤）、按重要性加权、每个评分档给出"可验证的具体行为"（如"对话符合该角色人设且推进情节"）而非"文笔深刻"式抽象描述。
2. **一票否决项（Veto）**（第7章）：与质量正交的致命硬伤应设为一票否决——设定前后矛盾（对应审稿界的"幻觉"）、关键伏笔未回收、不可修复的逻辑硬伤，无论其他维度多优秀都整体否决；书中实测 180 次评判中否决项触发 28 次，证明它真实改变结果而非装饰。
3. **LLM 评委校准（金标集）**（第7章）：放量用 LLM 审稿前，先请人类编辑对 100-200 个稿件片段打标（覆盖各类型与难度），测评委与人类一致率（kappa≥0.7）才启用；Rubric 或评判模型每次更新后重新校准——LLM 分数只是人类判断的可靠代理，不是真理。
4. **防长度偏差**（第7章）：LLM 评委天然倾向给更长、更详尽的文本高分，对小说审稿尤其危险（长≠好）；对策是 Rubric 显式惩罚冗长/规定篇幅上限，并定期审计"高分是否几乎总伴随长文本"，发现相关性则回炉 Rubric。
5. **防位置偏差（配对比较协议）**（第7章）：比较"原文 vs 修改版"或"A 结局 vs B 结局"时，交换展示顺序各评一次取平均，或仅当两次判决一致才计入；随机化展示位置让偏差在大样本下抵消。
6. **多源异构评判 + 异源互审**（第7章、第9章）：用不同模型家族的多个 LLM 评委分别审同一稿件（不同家族偏见正交，Agent/作者难以同时"欺骗"所有评委），相同 Rubric、加权平均或一致性检查聚合；创作/改写模型与评审模型也应用不同家族，能力不宜悬殊。
7. **失败归因：定位首个错误而非最后症状**（第7章）：审稿结论要标出问题类别、首次出现问题位置（第几章/哪段对话）并引用原文证据；后续问题往往是连锁反应，按"最早且能解释后续失败"的原则选主因，不要把最后的报错当成根因。
8. **分层验证结构：结果/过程/质量三层**（第9章）：把审稿拆成三层——结果层（情节是否闭环、目标是否达成，可用伏笔回收清单、时间线一致性、设定矛盾扫描做半自动化确定性检查）、过程层（是否符合类型规则与叙事逻辑）、质量层（文笔、氛围、情感共鸣，交给 LLM Rubric）；越靠下的层越应使用确定性规则而非主观打分。
9. **评判须引用证据、低置信不入结论**（第9章）：评委不能只给模糊总分，要逐维度给分并引用原文证据、说明理由（如"第 3 章第 2 场对话中 X 的行为与第 1 章设定矛盾"）；证据不足时明确表示不确定，低置信度评语不自动进入正式反馈或训练数据。
10. **对抗式评审 / 红队压测**（第7章）：主动构造"表面华丽但逻辑断裂""靠辞藻堆砌蒙混过关""刻意迎合评委偏好"的稿件测试审稿系统，防止 Rubric 被表面质量欺骗——评审能力需要用攻击性案例来验证。
11. **消融实验验证审稿维度贡献**（第7章）：对审稿系统做维度消融——逐个移除 Rubric 维度观察结论是否大变，找出真正驱动评分与改进方向的维度，修剪"特性债务"（如发现去掉"文笔"维度后结果几乎不变，说明它只是感觉有用）。
12. **区分机制指标与目标指标**（第7章 AB 测试方法论）：审稿优化中"长度、词汇丰富度、华丽程度、金句数量"是机制指标（你直接改的东西），"逻辑严密、情感共鸣、可读性、人物可信度"才是目标指标——不要把你改变的东西当作优化目标；同时设护栏指标（如"误杀好段落率""流畅度下降"超限即停止）。
13. **统计显著性与配对分析**（第7章）：判断"修改稿是否真的更好"要对同一批稿件新旧两版逐篇配对比较（McNemar/配对 bootstrap），多随机种子报告均值与波动；几十篇样本下 2-3 个百分点的差异只是噪声（SE≈√(p(1-p)/n)），不足以支撑结论。
14. **评估驱动的改进闭环（边界集+保留集）**（第7章、第9章）：把被否决的段落/硬伤沉淀为回归用例（"同类问题是否再犯"），新审稿标准或写作规则必须在硬伤边界集上改善、在原本优秀的保留集上不退化后才发布——防止为修一个毛病毁掉原有优点；审稿维度（Rubric）本身也要随案例不断迭代成"判例集"。
15. **渐进式信息透露 / 盲评**（第7章）：评审初期不暴露作者意图、大纲或"标准答案"，先盲评再逐步提供设定集与创作意图，防止评委被先验信息带偏；这对应 τ-bench 的核心原则——真实读者不会一上来就掌握全部信息。
16. **防数据泄漏**（第7章）：若审稿评估集取自经典名著片段或公开书评，很可能已进入训练语料，测的是记忆而非能力；应用新写/私有稿件或动态生成变体做评估，验证标准基于文本内容本身而非操作序列。
